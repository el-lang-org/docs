# Dependencies

V1 supports local path dependencies and Git dependencies pinned to a complete
commit hash.

## Declaring dependencies

Dependencies live in the `[deps]` table of `el.toml`:

```toml
[package]
name = "myapp"
namespace = "MyApp"
version = "0.1.0"

[deps.parser]
path = "../parser"
version = "0.3.0"

[deps.http]
git = "https://example.com/http.git"
rev = "0123456789abcdef0123456789abcdef01234567"
version = "1.2.1"

[target]
main = "Main"
```

## Rules

- A dependency selects exactly one of `path` or `git`.
- Versions are **exact**. Git revisions cannot be branches, tags, or abbreviated
  hashes.
- The dependency key must equal the dependency package's `package.name`.
- Executable projects commit `el.lock`, generated by resolution.

## Not in v1

- Registries and version ranges.
- Multiple versions of one package in the same dependency graph.

## Lockfile

`el.lock` records the resolved dependency graph. Use `--locked` with `check` or
`build` when the existing lockfile must not change:

```sh
el check --locked
el build --locked
```

## Native dependencies

Packages can declare C bindings with a `[native]` manifest table. Libraries and
frameworks use linker names, and the root package grants consent for every
foreign-declaring dependency through `allow`:

```toml
[native]
libraries = ["z"]
frameworks = []
allow = ["native_helper"]
```

The package itself needs `[native]` to declare `@extern` or directly use public
`Ffi` operations. Root consent also covers transitive dependencies; a
dependency-local allowlist cannot grant it. Missing lists are empty.
See [Native FFI](/std/ffi) for boundary types, memory ownership, and restrictions.
